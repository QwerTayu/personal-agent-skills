# review-subagent

レビューは、作業しているセッションとは別のエージェントに頼む。同じ文脈を持ったままだと、自分の書いたものを甘く見てしまうからだ。
レビュー役は Agent ツールで起こすサブエージェントで、`isolation: "worktree"` で自分の worktree の中で動く。作業ツリーを汚さずに、試しのファイルを置いたりコマンドを動かしたりできる。

## 1. 自分でレビューするか決める

次のどれかなら、サブエージェントに回さず、今のセッションで普通にレビューする（code-review / security-review を頼まれたなら、その skill をそのまま使う）。

- 自分が、この skill で起こされたレビュー役である（依頼文が「あなたはこの変更のレビュワーです」で始まっている）。レビュー役がさらにレビュー役を起こして終わらなくなるのを防ぐ。
- code-review に `--fix` か `--comment` が付いている（作業ツリーを書き換える、またはユーザーに確かめずに PR に投稿するので、レビュー役には回さない）。

## 2. 何をレビューするか決める

- **ローカルの変更**（作業ツリーやブランチのセルフレビュー）:

  ```sh
  git rev-parse --show-toplevel
  git branch --show-current
  git rev-parse HEAD
  git status --porcelain
  git fetch origin   # 比べる基点（ふつうは origin/main）を新しくする。リモートがなければ飛ばす
  ```

  サブエージェントの worktree は HEAD から作られ、まだコミットしていない変更は入らない。コミットしていない変更があれば、レビュー役に渡すために、scratchpad などリポジトリの外へ書き出す。

  ```sh
  out=<scratchpad のフォルダ>/review-input
  mkdir -p "$out"
  git diff HEAD --binary > "$out/uncommitted.patch"                  # 追跡しているファイルの変更
  git ls-files --others --exclude-standard -z > "$out/untracked.list"  # まだ追加していないファイルの一覧（NUL 区切り）
  ```

  まだ追加していないファイルは、レビュー役が元のリポジトリから読んでコピーする（パスは一覧のとおり）。`git add -N` などで作業ツリーやインデックスを触らない。

- **PR**: 番号か URL を渡されたとき、PR をレビューしてと頼まれたとき。

  ```sh
  gh pr view <PR 番号> --json number,url,headRefOid,baseRefName,headRepositoryOwner,title
  ```

  レビューするのは `headRefOid` の SHA と決めて、依頼に書く。PR が今のリポジトリのものでなければ、ユーザーに聞く。

## 3. サブエージェントを起こす

Agent ツールを、`subagent_type: "general-purpose"`、`isolation: "worktree"` で呼ぶ。前のレビューの内容を持ち込まないよう、レビューごとに新しく起こす（前のレビュー役に SendMessage で続きを頼まない）。

依頼文（`prompt`）は、次の形で書く。**自分の結論や、気にしている所への自分の見立ては書かない**（レビュー役がそれをなぞってしまうため）。何のための変更かという事実と、ユーザーが気にしている所だけを書く。

- **役割**: 「あなたはこの変更のレビュワーです」と書き出す。指摘は、そのまま PR のレビューコメントとして出せる文面で書いてもらう。依頼の経路（この skill やサブエージェントであること）には触れさせない。
- **種類**: ローカルか PR か。PR なら番号と URL。
- **対象と準備**: 今いる worktree で、まず次をしてもらう。
  - ローカル: 元のリポジトリのパス、ブランチ、HEAD の SHA。worktree が同じ SHA かを `git rev-parse HEAD` で確かめる。コミットしていない変更があれば `git apply <patch のパス>` で当てる。まだ追加していないファイルは、一覧が NUL 文字で区切られているので、`while IFS= read -r -d '' p; do mkdir -p "$(dirname "$p")"; cp "<元のリポジトリ>/$p" "$p"; done < <一覧のパス>` のように読んで、元のリポジトリからコピーする。見る差分は `git diff origin/main...HEAD` と `git diff HEAD`（リモートがなければ `main...HEAD`）。
  - PR: `git fetch origin pull/<番号>/head` と `git fetch origin <baseRefName>` のあと、`git checkout --detach <headRefOid>`。見る差分は `git diff origin/<baseRefName>...HEAD`。先に `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/comments`（インラインのコメント）と `gh api --paginate repos/<owner>/<repo>/pulls/<番号>/reviews`（レビュー全体のコメント）で、PR に今あるコメントを読む。`--paginate` がないと最初の 30 件しか返らない。すでに出ている指摘は出さない。
- **観点**: 頼まれた内容に合わせる。
  - セルフレビュー: 正しさ、書き漏れ、周りのコードとの食い違い
  - 敵対的評価: 壊れる入力や状態を積極的に探す。「たぶん大丈夫」で済ませない
  - code-review / security-review: レビュー役にその skill を使ってもらう（引数があればそのまま渡す。`--fix` と `--comment` は 1 で外してある）。そのうえで、結果を下の出し方に直してもらう
- **作業の背景**: 何のための変更か、ユーザーが気にしている所（事実だけ）
- **約束**:
  - 元のリポジトリ（ユーザーの作業ツリー）は読むだけで、書き換えない。書き換えてよいのは、自分の worktree の中だけ。
  - **確からしさが高でない指摘は、出す前に確かめる。** テストを動かす、小さなスクリプトや試しの入力で再現する、ビルドする、などで実際に動かし、高に上げる努力をする。確かめた指摘は、何を動かして何が起きたかを書く。どうしても確かめられないもの（外のサービスが要る、動かすのに時間がかかりすぎる、など）は、確からしさを中か低のまま残し、確かめられなかった理由を書く。読んだだけの推測で済ませない。
  - 動かすのに依存が要るとき（`npm install` など）は、worktree の中で入れてよい。ネットワークの外へ何かを送る操作（デプロイ、PR への投稿、メッセージの送信など）はしない。
  - worktree の片付けはしなくてよい（依頼した側が消す）。
  - 指摘ごとに、場所（`ファイル:行`）を書く。直してほしい点なら、何が起きるかと直し方も書く。
  - 指摘の先頭に、次のタグを 1 つ付ける。タグは重さを、確からしさはどれだけ確かかを表す。
    - `must:` 直さないとマージできない
    - `should:` 直したほうがよい
    - `ask:` 質問。答えがないと判断できない、意図や意味をつかむのに大事なこと
    - `imo:` 個人的な意見
    - `nit:` 細かい点
    - `info:` 直さなくてよい。知っておくとよいこと
    - `next:` この変更の範囲の外だが、改善できると気づいたこと
    - `good:` 特に良いと思った点
  - **指摘に番号を付ける。** 上のタグの順（must → should → ask → imo → nit → info → next → good）に並べ、同じタグの中はファイルと行の順にして、上から R1, R2, R3 … と振る。
  - 出し方（指摘ごと）:

    ```
    R1 must: <ひとことで何が問題か>（path/to/file.ts:42）
       何が起きるか: …
       直し方: …
       確からしさ: 高（動かして確かめた: <コマンドと結果>）
    ```

    最後に、確かめに動かしたコマンドの一覧と、確かめられなかった指摘とその理由をまとめる。指摘がなければ、そう書く。

起こしたら、レビュー役が終わるのを待つ。裏で動かしたときは、終わった知らせが届くまで、結果を想像で書かない。

レビュー役の worktree は、作業しているリポジトリの中の `.claude/worktrees/agent-…` に、ブランチ `worktree-agent-…` で作られる。何も変えずに終われば自動で消えるが、パッチを当てた、依存を入れた、PR の SHA に checkout した、などで中身が変わっていると、worktree もブランチも残る。残ると、作業しているリポジトリの `git status` に `?? .claude/` と出て、`git add -A` でコミットに入ってしまう。
そのため、結果を受け取ったら、依頼した側が必ず消す。終わった知らせ（または Agent ツールの結果）に、worktree の場所とブランチ名が付いてくる。

```sh
git worktree remove --force <worktree の場所>
git branch -D <ブランチ名>
rmdir .claude/worktrees .claude 2>/dev/null   # 空になったら消す（中にほかのものがあれば残る）
git status --short                            # .claude/ が出ていないことを確かめる
```

場所とブランチ名がわからなければ、`git worktree list` で `.claude/worktrees/agent-` の行を探す。自分が起こしたレビュー役のもの以外は消さない。

## 4. 結果を見せる

- レビュー役が返した指摘を、**番号もタグも文面も変えずに全部**ユーザーに見せる。自分で選んだり、まとめ直したり、確からしさを書き換えたりしない。
- 見せたうえで、自分の意見（同意できない指摘、すでに直っている指摘など）があれば、指摘とは分けて、番号を挙げて書く。
- **どれを直すかは、ユーザーが番号で選ぶ。** 選ばれるまで直さない。
- 番号はレビューごとに R1 から振り直す。同じセッションで 2 回以上レビューしたときは、どのレビューの番号かを書き添える（「2 回目のレビューの R3」）。話し合ってタグが変わっても、番号は変えない（「R2 は should に変更」と書く）。

## 5. PR に投稿するとき

PR へのコメントは外から見える操作で、ユーザーのアカウントで投稿される。必ずユーザーに確かめてから投稿する。

- 投稿するコメントを、タグ付きで見せて、投稿してよいかを確かめる。
- 投稿する本文は、タグ（`must:` など）で始める。**R1 などの番号、確からしさ、依頼の経路は入れない**（PR にはほかのレビューのコメントもあり、番号は意味を持たないため）。
- 投稿する直前に、`gh pr view <番号> --json headRefOid` が、レビューした SHA と同じかを確かめる。違えば（レビューのあいだに push された、など）行番号がずれるので、投稿せずにユーザーに伝える。
- 投稿するときは、レビュー API（`gh api repos/<owner>/<repo>/pulls/<番号>/reviews`）の `commit_id` に、レビューした SHA を渡す。
